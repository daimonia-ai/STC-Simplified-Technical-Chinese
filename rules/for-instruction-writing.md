# for instruction writing

适用于写给 agent 照着执行的文字：系统提示词、AGENTS.md、CLAUDE.md、skill，以及给 agent 的工作流程和规范。读者是模型。

本档管的是这类文字本身怎么写。把 STC 的核心规则贴进 AGENTS.md，是安装 STC 的方式，四个档位都靠这一步；往 AGENTS.md 里新写一条规则时，这条规则按本档写。

通用规则（[`general.md`](general.md)）同样适用。

### I1 强度只用“应、宜、可、能”及其否定

要求的强度应只用下表里的助动词，含义照 GB/T 1.1—2020：

| 强度 | 肯定 | 否定 |
|---|---|---|
| 要求 | 应 | 不应 |
| 推荐 | 宜 | 不宜 |
| 允许 | 可 | 不必 |
| 能力或可能 | 能 | 不能 |

不应使用“必须、务必、一定要、禁止、严禁、切勿、不要、尽量、最好”表达强度。这些词应按不推荐写法表换成上表里的词。

要求写“应”，不应写“应该”。“应该”在日常用法里偏向建议，读者分不清是要求还是推荐。

按顺序执行的操作步骤可以写成以动词开头的祈使句，不必加“应”。GB/T 1.1—2020 同样允许在步骤里用祈使句表示要求。

原因：同一份规则里混用多个强度词，模型分不出哪条更重。固定成四组词，每条规则的强度一眼就能读出。

- ✗ 必须先运行测试。禁止直接推送到主分支。尽量写单元测试。
- ✓ 推送前应运行测试。不应直接推送到主分支。宜为新函数写单元测试。

### I2 “尽量”“避免”这类词不与“应”连用

“尽量、尽可能、考虑、避免”不应与“应”连用。要表达推荐，应改用“宜”。

原因：“应尽量”一半是要求、一半是推荐，模型不知道做不到时算不算违反。

- ✗ 应尽量减少新增依赖。
- ✓ 宜减少新增依赖。
- ✓ 新增依赖前，应在提交说明里写明理由。

### I3 一条只写一个要求，例外写在同一条里

一条规则应只写一个要求。这条要求的条件和例外，应写在同一条里。

原因：几个要求写在一条里，例外适用于哪一个就说不清。

- ✗ 提交前应运行测试并更新文档，紧急修复除外。
- ✓ 提交前应运行测试。
- ✓ 提交前应更新文档。紧急修复可先提交，24 小时内补上文档。

### I4 写清触发条件、对象和动作

每条规则应写清三件事：什么时候、对什么、做什么。不应写“必要时、适当时、视情况”。

- ✗ 必要时通知负责人。
- ✓ 部署失败时，应通知项目负责人。

### I5 要求和理由分开写

要求和理由宜分开写：要求在前，理由另起一句，以“原因：”开头。规则正文里不宜讲事情的经过。

- ✗ 上次有人直接推送导致大文件丢失，花了两天才找回，所以以后推送都要用同步脚本。
- ✓ 推送应使用同步脚本。原因：直接推送会漏传大文件。

### I6 写出名称或路径，不写“上面那个”

指称对象时，应写出名称、路径或编号。不应写“上面那个、这个文件、之前说的”。

原因：规则会被单独引用，也会被不同的会话读到，上下文不一定在。

- ✗ 改完后同步更新那个配置。
- ✓ 改完后同步更新 `config/app.yaml`。

### I7 同一条要求只在一处写

同一条要求应只在一处写。其他地方需要时，应写指向，不应复制。

原因：复制到几处的要求，改的时候容易漏掉一处，几处说法就不一致了。

- ✗ 在三份规则文件里各写一遍“提交说明用中文”。
- ✓ 在一份规则文件里写“提交说明用中文”，另两份写“提交说明的写法见 `CONTRIBUTING.md`”。

### I8 要求写成能检查的形式

要求宜写成能检查的形式：读的人能判断“做了”还是“没做”。

- ✗ 代码要写得简洁。
- ✓ 函数不应超过 50 行。
