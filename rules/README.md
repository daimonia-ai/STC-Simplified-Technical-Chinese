# STC 规则

STC 的规则分两层：

- **通用规则**（[`for-all.md`](for-all.md)）：所有文字都适用，编号 G。
- **场景规则**：按在写哪类文字分四个场景，补充通用规则。两者不一致时，以场景规则为准。

| 场景 | 文件 | 编号 |
|---|---|---|
| for chat | [`for-chat.md`](for-chat.md) | C |
| for document | [`for-document.md`](for-document.md) | D |
| for web dev | [`for-web-dev.md`](for-web-dev.md) | W |
| for instruction writing | [`for-instruction-writing.md`](for-instruction-writing.md) | I |

## 先判断场景

按读者和用途判断：

| 读者 | 用途 | 场景 |
|---|---|---|
| 正在对话的人 | 得到回复 | for chat |
| 人 | 理解内容或照着操作：报告、方案、手册、会议纪要、代码注释、提交说明、日志 | for document |
| 产品的用户 | 在网页或应用界面上看到 | for web dev |
| agent | 照着执行：系统提示词、AGENTS.md、CLAUDE.md、skill、给 agent 的工作流程 | for instruction writing |

同一份文字只按一个场景写。一份文档里引用界面文字时，被引用的界面文字按 for web dev 写，文档本身按 for document 写。

## 规则里的强度词

STC 的规则本身按 for instruction writing 写。强度分四级，结构参考 GB/T 1.1—2020；要求一级用“必须、不得”，不用国标的“应、不应”，因为“应”在日常用法里容易读成“应该”：

| 词 | 含义 |
|---|---|
| 必须 / 不得 | 要求，做不到就不符合 STC |
| 宜 / 不宜 | 推荐，有理由时可以不照做 |
| 可 / 不必 | 允许 |
| 能 / 不能 | 能力或可能 |

## 每条规则的写法

每条规则包含一句规则、原因和例子；需要补充的信息写在“说明”里。例子里“✗”是不推荐的写法，“✓”是推荐的写法。例子使用通用名称，不针对任何真实的个人或企业。

## 规则一览

### 通用规则

| 编号 | 规则 |
|---|---|
| G1 | 一个意思只用一个词 |
| G2 | 产品名、功能名、指标名照项目术语表写 |
| G3 | 用推荐词，按词表替换不推荐写法 |
| G4 | 动作直接写成动词 |
| G5 | 程度词和模糊量词换成数字或具体事实 |
| G6 | 不用营销词和套话 |
| G7 | 不用口号句式 |
| G8 | 缩写和代号第一次出现时附全称或解释 |
| G9 | 一句只讲一件事 |
| G10 | 条件写在前面 |
| G11 | 用主动句 |
| G12 | 控制句子长度 |
| G13 | 名词前的修饰语不超过 3 层 |
| G14 | 否定词和限定词不省略 |
| G15 | 保留表示把握程度和频率的词 |
| G16 | 代词只指上文里明确的名词 |
| G17 | 标点照 GB/T 15834—2011，引号用“” |
| G18 | 数字照 GB/T 15835—2011 |
| G19 | 中文与英文、数字之间空一格 |
| G20 | Anti-Echo：只写当前读者需要的内容 |
| G21 | 用自然的完整句子 |
| G22 | 篇幅由任务需要决定 |

### for chat

| 编号 | 规则 |
|---|---|
| C1 | 自称“我”，称对方“你”；说到组织写名称 |
| C2 | 第一句回答问题 |
| C3 | 不寒暄，不复述问题，不用感叹号 |
| C4 | 说到事实和数字给出处 |
| C5 | 长回答整理成文档或列表 |
| C6 | 主动发起对话时说清三件事 |
| C7 | 同一个结论只说一次 |
| C8 | 工具调用只说明有用的变化 |
| C9 | 结构跟着内容走 |

### for document

| 编号 | 规则 |
|---|---|
| D1 | 主语写名称，不写“我们”“你们” |
| D2 | 先写结论，再写依据 |
| D3 | 一段只讲一个主题 |
| D4 | 三项以上用列表 |
| D5 | 操作步骤一步一个动作，说明与步骤分开 |
| D6 | 风险提示先写动作或条件，再写后果 |
| D7 | 提醒分三级：警告、注意、说明 |
| D8 | 代码注释写原因，提交说明先写改了什么 |

### for web dev

| 编号 | 规则 |
|---|---|
| W1 | 不用复数人称代词和第三人称代词 |
| W2 | “你”指用户，“我”只出现在用户的原话里 |
| W3 | 按钮以动词开头，用推荐的动作词 |
| W4 | 同一个功能在各处同名 |
| W5 | 报错说清发生了什么、接下来能做什么 |
| W6 | 空状态说明这里会出现什么、怎么开始 |
| W7 | 说明文字讲“是什么、怎么读”，不讲操作 |
| W8 | 一句界面文字写成一个完整的字符串 |
| W9 | 页面文字服务当前用户 |

### for instruction writing

| 编号 | 规则 |
|---|---|
| I1 | 强度只用四组固定的词 |
| I2 | “尽量”“避免”这类词不与“必须”连用 |
| I3 | 一条只写一个要求，例外写在同一条里 |
| I4 | 写清触发条件、对象和动作 |
| I5 | 要求和理由分开写 |
| I6 | 写出名称或路径，不写“上面那个” |
| I7 | 同一条要求只在一处写 |
| I8 | 要求写成能检查的形式 |
